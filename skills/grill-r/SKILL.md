ユーザーは「このあたりが怪しい」という感覚しか持っていない。その正体を突き止め、根本から直す。
症状を1つ潰して終わらせず、それを生んだ設計上の判断まで遡り、同じ根から生えた欠陥ごと刈り取る。
ただし何をどこまで直すかは独断で決めず、議論で決める。

**調査 → 議論 → 記録 → 実装 → レビュー。記録まで進んだら止まり、ユーザーの合図を待って実装に入る。**

## 調査

深掘りは自分で行う。同時にセカンドオピニオンを1体、独立に走らせる。**渡すのはユーザーの元の違和感と対象範囲だけ。自分の仮説は渡さない** 一致すれば確信が上がり、食い違えばそこが本当に見るべき場所である。

成果物は2つ。どちらも推測を断定として報告せず、根拠は `ファイル:行` で示す。

- **再現筋道が説明できる直接原因** — 「この辺が怪しい」で止めない。症状の癖（「押すと直るが放っておくとズレる」など）まで説明できたなら掴んでいる
- **同じ原因系の欠陥台帳** — 同じ根から生えた/生えうる他の欠陥。これがリファクタリングを正当化する重みになる。1件だけなら応急処置で十分という結論もありうる

## 議論

調査結果を提示してから始める。台帳を見せずに「対症療法か全面再設計か」と聞いても判断できない。質問は一度に1つ、推奨と理由を添えて。コードを読めば分かることは調べる。

**まず修正スコープを問う。** ここが決まらねば他の質問は意味を持たない。議論するかどうかを決めるゲートなので、**質問数に数えず、答えを見てから残りを決める**。

- **A. 対症療法** — 症状だけ直す。原因は残り再発する
- **B. 構造の作り直し** — 症状を生んだ設計を直す。同じ原因系がまとめて消える
- **C. 全面再設計** — その領域を作り直す

推奨は台帳の重みから決める。Aや「直さない」で決着したら議論を終え、以降の工程も軽くしてよい。BかCなら、あと何を決める必要があるかを見極めて、質問数を宣言し（3・5・8から選ぶ）、対象固有の分岐を上流から順に問う。各質問に対し、推奨回答も併せて提示する。

## 記録

実装前に GitHub Issue を立てる。着手前が、ユーザーが止められる最後の機会になる。Issue 運用の慣例がなければ、立ててよいか確認する（外向きの作成物なので）。Git管理でない場合、同等の管理をする慣例があれば従う（ローカルタスクチケット・Redmineチケット等）

書くのは、症状 / 原因 / 欠陥台帳 / 議論の要約 / Before/After。**Before/After の主役は設計の姿** — 全差分は PR が持つので、ここには差分を見ても分からないことを書く。コードは判断が凝縮した1〜2箇所で足りる。

## 実装

直してよいのは**議論で決めた方針と、同じ原因系の欠陥**だけ。根の別な問題を混ぜると「なぜこの変更が入っているのか」を追えなくなる。範囲外の問題は課題台帳かユーザーへの報告に必ず残す。

- 本不具合の**再現テストを1件以上**書く（著しく困難なら省略してよいかユーザーに確認）
- 挙動が変わるなら明示する。リファクタリングは「何も変わらないはず」という期待を裏切りやすい
- **新しい設計が成り立つ前提を書き残す。** 「この方式が安価なのは◯◯だから」を書かなければ、次に触る人が前提ごと壊す。記録ではなく退行防止装置である

更新すべき文書があれば慣例に従い更新する。状態やBefore は設計文書に書かない — 現在の姿を書く場所で履歴は残すべきでない

## レビュー

実装後、適切に観点を分け並列レビューを行う。
範囲は**マージ先からの実差分**で指定する。広く渡すと自分が触っていない変更まで対象になり、誤検知が混ざる。
指摘は鵜呑みにせず裏を取ってから採否を決め、**全件に採否と理由を残す**（誤検知ならその根拠を）。
