# 図の規則の細部

`SKILL.md` の「規則」と「描いたあとの確認」を補う細部と根拠である。`SKILL.md` に書いた決まりは、ここでは繰り返さない。文書用の図を描くとき、校閲を頼むとき、検査の結果の読み方に迷ったときに読む。

## 記号と配置

- 順序だけを表す矢印は、本文やキャプションで一度言えばラベルを省いてよい。
- 矢印の上やそばに、流れの説明でない記号(検査する地点、境界、番号)を置くときは、`references/elements.md` の「矢印に付ける記号」に従い、形で意味を分ける。
- 始まりと終わりがある過程は円で描かず、直線と戻りの矢印で描く。環そのものが主張なら円でよい。
- 大きさに意味を持たせないときは、同じ種類の要素の大きさをそろえる。
- 要素の数の目安(5〜8 個)は、研究の裏付けの無い目安である。
- 記号だけで意味を伝えない。飾りの絵は描かない。量は記号の大きさでなく、数か文字で示す。
- 強調には、人が確かめる段や図の結論に当たる部分を、濃い塗りなど 1 つの手段で目立たせる。

## 文字

- 文書に載せる図では、補足の説明は図の外の本文に書く。段落が要る説明は図に入れない。
- 題と本文で同じ文を繰り返さない。本文の図のすぐ前後では、題を言い換えず、図を読む手がかりを書く。
- 範囲を言う必要があるときだけ、題の後ろか本文のキャプションに書く。パターン名は読み手に要らない。
- シンプルな図で要る説明が字数の上限を超えるときは、先に要素を減らすかズームの 2 枚に分けることを検討し、それでも要るなら残す。
- 番号は、本文の表に結ぶ長い説明があるときに使う。番号の一覧を枠の外にまとめ、長い説明だけを本文の表に置く。図だけを見た人が番号の意味を読めないなら、その図は不完全である。
- 凡例の見本に、図で使っている番号を使わない。読み手は、見本の番号にだけ説明があると読む。番号の種類を色で分けるときは、一覧を種類ごとの見出しの下に並べ、見出しで色の意味を言う。
- 文字は少ないほど良いのではない、という考えは Mayer の一貫性原則による。ラベルを図から抜くと図の効果は消える。
- 字数の目安は、研究ではなく実務の経験則(越川の 1 枚 105 字、Alley の見出し 2 行、Yahoo! ニュースの見出し 15.5 字)と、C4 や Kubernetes の公式の図の観察から決めた。字の大きさの 3 段も、研究の裏付けの無い決まりである。
- 3 秒見て題の主張が分かるかの確認は、Duarte の Glance Test による。
- 図が文章より速く読める理由は、Larkin と Simon の「Why a Diagram is (Sometimes) Worth Ten Thousand Words」(Cognitive Science 11(1), 65–100, 1987, doi:10.1111/j.1551-6708.1987.tb00863.x)による。同じ情報を持つ図と文章でも、計算の効率は違う。図は情報を位置で整理するので、推論に要る情報が 1 か所にそろい、探す手間が少なくて済む。そうならない図は、文章より速くならない。
- 近くに置いたものや似たものを 1 つのまとまりと読む性質は、ゲシュタルト心理学の近接の要因と類同の要因である。原典は Wertheimer の「Untersuchungen zur Lehre von der Gestalt II」(Psychologische Forschung 4, 301–350, 1923, doi:10.1007/BF00410640)である。

## 語彙

- 実務者がふつうに使う語の例は、キャッシュの図なら「キャッシュヒット」、品質管理なら「作り込み」「流出」、EC なら「キャンセル」である。
- AI が書きがちな言い換えを避ける。例は「写し」(キャッシュ・コピー)、「〜を通す」(処理する・経由する)、「〜を担う」、英語の直訳、比喩の動詞である。直しすぎて硬い漢語にもしない。
- 資料の例は、IPA、JIS、JSTQB、公式ドキュメントの日本語版、官公庁などである。文書用の図では、確かめた資料を本文の脚注か作業記録に残す。
- 定義どおりに描くモデルには、V 字モデル、UML、BPMN、C4 モデル、特性要因図、ステージゲート、サービスブループリントなどがある。題材や見た目の都合で段を足したり組み替えたりしない。定義に揺れがあるときは、どの資料に従ったかを desc に書く。
- 対になる語は、それぞれの分野の定番の組で書く(V 字モデルなら、SQuBOK のとおり「実装」と「単体テスト」、「詳細設計」と「結合テスト」)。
- 同じ種類のラベルの形は、矢印は動詞で終える、段の名前は名詞にする、などを 1 枚の中で混ぜない。
- 数値の出典は図の最下部に書く(`references/numbers.md`)。パターン帳の作例だけは、架空と明記して架空の数値を使ってよい。
- 仕組みや定義の説明(気象の用語、暗号の手順、プロトコルの手順など)も、専門用語と同じく資料で確かめる。

## 日本語の書き方

- 題と注記は、人が書いた業務文書として違和感の無い文にする。題の主語と述語をかみ合わせる。
- 助詞の取り違えに気をつける。「受注で登録する」(手段に読める)より「受注時に登録する」、「1 枚で 1 行」より「1 枚に 1 行」のように、関係が 1 通りに読める助詞を選ぶ。
- 読点の位置で意味が変わらないようにする(「見込み客の、移行の不安」のような区切りは避ける)。
- 日本語と英数字のあいだには半角の空白を入れる(「4M で」「AI に」)。名詞の「受付」と動詞の「受け付ける」のように、送り仮名は品詞に合わせる。

## 校閲

文書用の図は、描いた本人以外の目で語彙と事実を校閲する。サブエージェントに任せるときは次を求める。

- 専門用語を変えるときも残すときも、確かめた資料の URL を添える。
- 資料が見つからない語は、根拠が弱いと明記する。
- 直した結果に `scripts/check.py` をかけ、字数の上限と PNG での見た目を確かめる。校閲で文字が長くなり、上限を超えることが多い。

## SVG

- Linux で日本語の書体が無いと、中国語の書体で描かれて字形がおかしくなる。PNG で確かめるときは、日本語の書体で描かれているかも見る。
- 太字を持たない書体(IPA Pゴシックなど)では、ブラウザが疑似ボールドで描き、画数の多い字が潰れる。PNG で太字の見た目を判断するときは、太字を持つ日本語の書体(Noto Sans CJK JP など)を入れてから描く。
- 意味を表す絵記号(人・書類・鍵など)は、単純な図形で描くなら使ってよい。

## 検査の読み方

- 検査は WCAG 2.x の式で、文字は 4.5:1、枠線は隣の色に対して 3:1 を下限にする。
- 重なりの検査は、文字どうし、文字と記号(`<use>`)、文字と線(細い罫線を含む)の重なりを見る。線と文字のあいだに塗りの図形を敷いた場合、背景色の縁取り(`paint-order: stroke`)を付けた文字、取り消し線は重なりとしない。
- 字数と 1 行の長さの検査は、半角の文字も 1 字と数える。詳細図でパスや識別子を残したときの指摘は、意図して外したものとして扱ってよい。
- PNG は Edge か Chromium のヘッドレスモードで描画する(環境変数 `DIAGRAM_BROWSER` でブラウザを指定できる)。`--out` は PNG を書き出すフォルダで、図の名前の PNG がその中にできる。PNG を案件のリポジトリに置くかどうかは案件の慣例に従い、確認のためだけなら作業用の場所に書き出す。
- GitHub では閲覧する端末の書体で表示されるため、PNG と字幅が少し違うことがある。箱の右端には 1 字分の余裕を残す。
- 案件に alt の書き方の慣例があれば、それにそろえる。長い説明は alt ではなく本文に置く。
