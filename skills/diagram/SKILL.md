# diagram

説明図を、パターン帳の作例を手本にして手書きの SVG で描く。図 1 枚で言うことは 1 つに絞り、その 1 文を題にする。

## モードを決める

| モード | 使う場面 | 手順 |
|---|---|---|
| 理解用 | 会話の中で 1 回見て捨てる図 | ブリーフは結論の 1 文だけ。描いたあと、元の文章との突き合わせと語彙の確認だけを行う |
| 文書用 | GitHub の文書・ポスター・スライドなどに残す図 | ブリーフを 5 行で書き、確認の手順をすべて行う |

規則は 2 つのモードで共通である。理解用の図を後で文書用に上げるときは、文書用の確認をやり直す。

## 描く前に書くブリーフ

文書用では次の 5 行を書いてから描く。理解用では 2 行目だけを書く。

1. **読み手**: 誰が、どこで読むか(例: 部門長がレビュー会で、GitHub の README で)。
2. **結論**: 図で言う 1 文(15〜25 字)。これを図の題にする。
3. **パターン**: `patterns/README.md` の目次から最も近いものを選ぶ。
4. **記号の割り当て**: どの色・線種・矢印に何の意味を当てるか。案件側に対応表があればそれに従う。
5. **本文との対応**: 図と本文で同じ語を使う箇所、番号で結ぶ箇所。

## パターン帳を引く

`patterns/README.md` の目次を「伝えたいこと」から引き、選んだパターンの作例の SVG を読んでから描く。作例の格子・寸法・記号の使い方を手本にし、中身は自分の題材で書く。

- どのパターンにも当てはまらないときは、近い 2 つを組み合わせるか、全体図と拡大図(ズーム)の 2 枚に分ける。
- Web や書籍の図も手本にしてよい。ただし学ぶのは技法だけで、構図・絵柄・文言は写さない。
- 数字やグラフを載せる図は、`references/numbers.md` の決まりにも従う。

## 共通の規則

この節の規則は原則である。個別の図で、意図があって外すのはかまわない。外したことで読み手が誤るかどうかは、描いたあとの確認で見る。

### 記号

- 1 つの色、1 つの線種、1 種類の矢印には、1 つの意味だけを当てる。意味は色だけでなく、形・線種・位置でも示す。
- 意味の割り当ては文書のまとまり(1 つのリポジトリ、1 つの発表)ごとに決め、その中では変えない。案件側に対応表のファイル(例: `docs/diagram-legend.md`)を置く。値は `references/palette.md` の色の枠から選ぶ。
- 意味を持つ矢印には動詞のラベルを付ける。節点・ラベル・節点で 1 文として読めるかで確かめる。順序だけを表す矢印は、副題で一度言えばラベルを省いてよい。
- 双方向の矢印は使わず、向きごとに 2 本に分ける。
- 矢印の上やそばに、流れの説明でない記号(検査する地点、境界、番号)を置くときは、`references/elements.md` の「矢印に付ける記号」に従い、形で意味を分ける。

### 配置

- 矢印が無関係な要素を横切らないようにし、線どうしの交差も減らす。
- 始まりと終わりがある過程は円で描かず、直線と戻りの矢印で描く。環そのものが主張なら円でよい。
- 1 枚の抽象度をそろえる。合わない細部は削り、ズームの 2 枚目に回す。
- 要素は 5〜8 個を目安にする。超えたら主張を絞るか、ズームで分ける。この数は研究の裏付けの無い目安である。
- 大きさに意味を持たせないときは、同じ種類の要素の大きさをそろえる。
- 単純化のために事実と違う包含関係や位置関係を描かない。

### 視覚要素

- まとまりは、余白と整列、背景の色の面、枠の順に検討する。箱(枠)は、余白と色の面で足りないときだけ使う。
- 要素の種類(人・書類・データベース・画面など)は、絵記号とラベルの組で示す。記号は `references/icons.svg` から写し、図ごとに描き起こさない。
- 時間軸・引き出し線・吹き出し・○△×・繰り返しの記号など、箱と線以外の要素の使いどころは `references/elements.md` にある。
- 記号だけで意味を伝えない。飾りの絵は描かない。量は記号の大きさでなく、数か文字で示す。

### 強調

- いま話している部分だけに色を付け、関係しない部分は灰色にする。
- 人が確かめる段や、図の結論に当たる部分を、濃い塗りなど 1 つの手段で目立たせる。強調の手段を 1 枚の中で増やさない。

### 文字の量

文字は少ないほど良いのではなく、主張に関係のない文字を載せないことが大事である(Mayer の一貫性原則)。ラベルを図から抜くと図の効果は消えるため、要る文字は残す。目安は次のとおりで、題を含め、図の中に描く文字をすべて全角で数える。

| 項目 | 文書用(幅 640) | ポスター(1280×720) |
|---|---|---|
| 1 枚の字数 | 60〜120 字。150 字を超えない | 40〜100 字。105 字を超えない |
| 題 | 主張の 1 文で 15〜25 字、1 行 | 主張の 1 文で 13〜25 字、2 行以内 |
| 要素の見出し | 名詞で 4〜10 字 | 名詞で 2〜8 字 |
| 矢印のラベル | 動詞句で 2〜8 字 | 動詞句で 2〜6 字 |
| 要素の補足 | 0〜1 行、20 字以内。補足を付けるのは要素の半数以下 | 図全体で 3 か所まで、各 15 字以内 |

- 副題は付けない。パターン名は読み手に要らない情報である。範囲を言う必要があるときだけ、題の後ろか本文のキャプションに書く。
- 文書に載せる図では、補足の説明は図の外の本文に書く。段落が要る説明は図に入れない。
- 題と本文で同じ文を繰り返さない。本文の図のすぐ前後では、題を言い換えず、図を読む手がかりを書く。
- 字数の上限は、図を読むのに要る文字(番号・記号・色の意味の説明)を削ってまで守らない。要る説明で上限を超えるときは、先に要素を減らすかズームの 2 枚に分けることを検討し、それでも要るなら残す。
- 描き終えたら、3 秒見て題の主張が分かるかを確かめる(Duarte の Glance Test)。
- 字数の目安は、研究ではなく実務の経験則(越川の 1 枚 105 字、Alley の見出し 2 行、Yahoo! ニュースの見出し 15.5 字)と、C4 や Kubernetes の公式の図の観察から決めた。

### 文字の置き方

- 図の最上部に題(結論の 1 文)を置く。
- 短い説明は、図の部品のすぐそばに直接書く。番号は、本文の表に結ぶ長い説明があるときに使う。
- 番号を付けたら、すべての番号に図の中で 1 行の説明を付ける。番号の一覧を枠の外にまとめ、長い説明だけを本文の表に置く。図だけを見た人が番号の意味を読めないなら、その図は不完全である。
- 凡例の見本に、図で使っている番号を使わない。読み手は、見本の番号にだけ説明があると読む。番号の種類を色で分けるときは、一覧を種類ごとの見出しの下に並べ、見出しで色の意味を言う。
- 凡例が要るときは枠の外に置く。
- 字の大きさは 3 段にする。文書用(幅 640)は題 20、見出しと項目 16、補足 14。ポスター(1280×720)は題 48 前後、見出し 28 前後、補足 18 前後。これも研究の裏付けの無い決まりである。
- 太字の日本語は 1 字がほぼ字の大きさの幅になる。箱の幅は「字数×字の大きさ+左右の余白」で見積もる。英数字はおよそ 0.6 字分である。
- 文は句の切れ目で改行する。1 行は全角 30 字までにする。

### 語彙

- 図の文字は、その図を使う分野の実務者がふつうに使う語で書く(キャッシュの図なら「キャッシュヒット」、品質管理なら「作り込み」「流出」、EC なら「キャンセル」)。
- AI が書きがちな言い換えを避ける。例は「写し」(キャッシュ・コピー)、「〜を通す」(処理する・経由する)、「〜を担う」、英語の直訳、比喩の動詞である。直しすぎて硬い漢語にもしない。
- 手法・工程・役割・状態などの専門用語は、その分野で権威のある日本語の資料(IPA、JIS、JSTQB、公式ドキュメントの日本語版、官公庁など)で使われている語にする。感覚で「ふつう」と判断しない。文書用の図では、確かめた資料を本文の脚注か作業記録に残す。
- 規格や提唱者の定義があるモデル(V 字モデル、UML、BPMN、C4 モデル、特性要因図、ステージゲート、サービスブループリントなど)は、段の数・名前・対応・記号を定義どおりに描く。題材や見た目の都合で段を足したり組み替えたりしない。定義に揺れがあるときは、どの資料に従ったかを desc に書く。
- 対になる語は、それぞれの分野の定番の組で書く(V 字モデルなら、SQuBOK のとおり「実装」と「単体テスト」、「詳細設計」と「結合テスト」)。
- 同じ図の中で、同じものを違う語で呼ばない。図の注記と、図が指す画面や文書の文言も一致させる。
- 同じ種類のラベルは形をそろえる。矢印は動詞で終える、段の名前は名詞にする、などを 1 枚の中で混ぜない。
- 架空の数値・統計・固有名を入れない。事実に自信が無い部分は図から外す。数値を載せるときは出典を図の最下部に書く(`references/numbers.md`)。
- 仕組みや定義の説明(気象の用語、暗号の手順、プロトコルの手順など)も、専門用語と同じく資料で確かめる。

### 日本語の書き方

- 題と注記は、人が書いた業務文書として違和感の無い文にする。題の主語と述語をかみ合わせる。
- 助詞の取り違えに気をつける。「受注で登録する」(手段に読める)より「受注時に登録する」、「1 枚で 1 行」より「1 枚に 1 行」のように、関係が 1 通りに読める助詞を選ぶ。
- 読点の位置で意味が変わらないようにする(「見込み客の、移行の不安」のような区切りは避ける)。
- 日本語と英数字のあいだには半角の空白を入れる(「4M で」「AI に」)。名詞の「受付」と動詞の「受け付ける」のように、送り仮名は品詞に合わせる。
- 日本語の文の書き方の規範を持つスキル(例: `readable`)があれば、それにも従う。

### 校閲

文書用の図は、描いた本人以外の目で語彙と事実を校閲する。サブエージェントに任せるときは次を求める。

- 専門用語を変えるときも残すときも、確かめた資料の URL を添える。
- 資料が見つからない語は、根拠が弱いと明記する。
- 直した結果に `scripts/check.py` をかけ、字数の上限と PNG での見た目を確かめる。校閲で文字が長くなり、上限を超えることが多い。

### SVG

- 手書きの静的 SVG にする。Mermaid・HTML・`foreignObject`・外部の画像や書体の読み込みは使わない。
- 最初の要素に全面の背景の矩形を描く。GitHub のダークテーマでも読めるようにするためである。
- `<title>` に題を、`<desc>` に図の中身を文で書く。
- `font-family` は `'BIZ UDPGothic','Yu Gothic UI','Meiryo','Hiragino Sans','Noto Sans JP',sans-serif` にする。
- 意味を持たない影・グラデーション・背景の絵を使わない。意味を表す絵記号(人・書類・鍵など)は、単純な図形で描くなら使ってよい。

## 描いたあとの確認

| 確認 | 理解用 | 文書用 |
|---|---|---|
| 元の文章との突き合わせ(ラベル・矢印の向き・要素の抜け) | 行う | 行う |
| 語彙と日本語の確認(上の「語彙」「日本語の書き方」の規則) | 行う | 行う |
| 描いた本人以外による校閲(上の「校閲」の規則) | 不要 | 行う |
| `scripts/check.py` でコントラスト・背景・字数・重なりを確かめる | 行う | 行う |
| PNG に描画して目で見る(はみ出し・重なり・改行) | 任意 | 行う |
| Markdown の alt に、何の図かと結論が分かる短い文を書き、長い説明は本文に置く。案件に alt の書き方の慣例があればそれにそろえる | 不要 | 行う |

```bash
python ~/.claude/skills/diagram/scripts/check.py 図.svg --png --out <PNG の書き出し先>
```

- 検査は WCAG 2.x の式で、文字は 4.5:1、枠線は隣の色に対して 3:1 を下限にする。
- 重なりの検査は、文字どうし、文字と記号(`<use>`)、文字と太さ 1.5 以上の線の重なりを見る。文字の幅は字数からの見積もりなので、検査を通っても PNG で値のラベルと線の間を目で確かめる。ラベルが線や軸に重なる図は、どのモードでも出さない。
- PNG は Edge か Chromium のヘッドレスモードで描画する(環境変数 `DIAGRAM_BROWSER` でブラウザを指定できる)。PNG を案件のリポジトリに置くかどうかは案件の慣例に従い、確認のためだけなら作業用の場所に書き出す。
- GitHub では閲覧する端末の書体で表示されるため、PNG と字幅が少し違うことがある。箱の右端には 1 字分の余裕を残す。

## 避ける作り方

- 凡例が無く、色や線に意味の無い箱と線の集まり。
- ラベルの無い線、双方向の矢印。
- 1 枚に全部を載せた図。
- 主張の無い図(「ここに情報がある」だけの図)。
- 製品のロゴを概念の要素として並べた図。
